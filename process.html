Development Process

人机协作开发时间线

本项目通过“原始交互日志 + 阶段反思”记录每一次有意义的人机协作。下方为精选手时间线，完整记录见 agent-development-log.md。

Interaction阶段 0 · 项目初始化

从设计 Brief 出发

学生请求：基于 development-brief.md（Sailing First Playable Web Game Brief）与系统图，启动一个帆船教学游戏。

  • 确立核心学习转变：新手“指向目标”，专家“读风并调整船/帆/航线”。
  • 确立核心循环：观察 → 判断 → 行动 → 反馈 → 调整。
  • 技术选择：首个可玩原型采用 Three.js + Vite（后于本次重构改为本地离线运行）。
Interaction阶段 1 · 可玩原型

3D 航海模拟原型跑通核心循环

Agent 实现：搭建场景/海面/天空、帆船模型、风场、帆空气动力、船体动力学、第三人称相机、HUD 与罗盘。

  • 风场（来向+风速，低频漂移）、帆效率曲线、横倾、船体积分。
  • 操作映射：A/D 转舵、W/S 调帆、Q/E 帆面积、空格回正。
  • HUD 显示航速/航向/风向/帆角/舵角/迎风角/调帆质量；罗盘显示禁航区、目标方位、风来向。
  • 随机目标浮标 + “目标到达”反馈。

测试：核心循环可在浏览器运行；但缺少关卡、限时、胜负、水流、礁石、展览网站与开发日志。

Reflection覆盖 Interaction 01–02

第一个可玩循环完成

  • 游戏变化：玩家可转舵调帆、看到风/帆/船的实时反馈。
  • AI 帮助：把“调帆→推力”的效率曲线做得足够陡峭，让调帆好坏有数量级差异。
  • 设计方向：原型偏“真实模拟”，与 brief 的“first playable、面向学习”有偏差——缺少明确挑战与胜负。
  • 与核心转变的关系：已能体现“调帆影响速度”，但尚未强制玩家“读风选路”。
⏳ 待学生反思：当前游戏是否让你体验到“读风而非指向目标”？哪些 AI 建议被你接受/修改？
Interaction阶段 2 · 系统化重构（本次）

面向成果展示的改造

学生请求：保留 3D 效果，但补齐展览网站、关卡/挑战、胜负、水流/礁石、开发日志；并把数据暴露在 UI 上方便调整设计。

  • Three.js 本地化（vendoring + importmap），去除 Vite/npm 运行依赖，支持离线静态运行。
  • 新增 index.html 主页、game.html 游戏页、process.html 过程页、styles.css 共享样式。
  • 新增 Level 1–3 关卡预设（横风 / 顶风限时 / 横风限时+礁石）。
  • 新增胜负系统：倒计时、船体血量、Win / Game Over 面板。
  • 新增水流系统（WaterCurrent）与礁石系统（RockField），含碰撞检测。
  • 新增设计面板（DesignPanel），实时暴露并调整风/水流/物理/关卡参数。
  • 补齐 agent-development-log.md 与 submission-manifest.json。

测试：本地静态服务器联调中；各页面与资源相对路径可达。

Reflection覆盖 Interaction 03

成果展示结构就绪

  • 游戏变化：从“无限随机浮标”变为“有目标、限时、避障、胜负”的关卡式学习。
  • AI 影响：重构将技术原型推向 brief 要求的提交/展览形态。
  • 与核心转变的关系：Level 2（顶风限时）强制玩家走之字形，直接对应“读风而非指向目标”。
⏳ 待学生反思：Level 2/3 的难度是否合适？设计面板暴露的参数是否足够你调整？是否要加入“航迹 vs 计划航线”对比反馈？
Interaction阶段 3 · UI 打磨与可读性

基于试玩的界面与可读性迭代

学生请求：用真实系统图替换占位图；全站中英文切换；将 HUD 从右侧移到左侧并整合为单一面板；增强目标浮标可见性；修正罗盘目标标记并补充关卡说明。

  • 系统图改用学生上传的“Sailing - Ian”设计图（Interaction 04）。
  • 新增 assets/i18n.js，全站文本与游戏 HUD/设计面板/胜负层支持中英切换并记忆语言（Interaction 05）。
  • HUD 整合为左侧单面板（关卡/导航/目标/帆舵/罗盘），不再遮挡场景与设计面板（Interaction 06–07）。
  • 目标浮标增大、改高对比亮色 + 远处 Sprite 标记 + 光柱；罗盘补回绿色目标方位标记（Interaction 08–09）。

测试：全部 JS 语法检查通过；LevelManager 逻辑测试 12/12；各页面与资源经本地静态服务器返回 200。

Interaction阶段 3 · 换舷机制

自动换舷：帆过风自动翻侧

学生决定：保留 3D 与“读风/调帆”学习，采用方案 A：船穿过风时帆自动翻到背风侧，玩家只需转舵 + 微调。

  • sailAngle 仅表示帆松开幅度，所在舷由 TWA 符号 + 15° 死区决定（避免禁航区内抖动误翻）。
  • Sailboat 据此镜像渲染帆；HUD 增加“舷 Tack”指示与换舷瞬间提示（视觉 + 轻微音效）。

测试：换舷判定单测 14/14 通过；改文件语法检查通过；各资源 200。

Interaction阶段 3 · 关卡节奏

礁石布局：从“岛屿”到“通道门”

学生反馈：Level 3 礁石太大，应挡住帆船与目标之间的通道，但从起点仍能看到目标。

  • 半径从 22-26 缩小到 10-13，视觉上更像礁石而非岛屿。
  • 在起点到目标 (0,0) → (0,-600) 的通道上布置 9 块礁石：中心线设第一道门，后续左右交错形成 S 形绕行路线。
  • 两侧补小礁石压缩通道，但不完全封死；目标浮标的光柱与高度保证从起点可见。

测试：levels.js 语法检查通过；服务器返回 200；等待试玩校准。

Interaction阶段 3 · 反馈打磨

换舷视觉反馈：从“听见”到“看见”

学生反馈：触发换舷后响了声，但风帆看起来仍在同一侧。

  • Sailboat 加左右舷航行灯：左舷（port）= 红，右舷（starboard）= 绿，提供持续参照。
  • 换舷时帆做 0.35 秒“甩过中心线再回稳”的动画，而非硬切。
  • HUD 舷指示按左红右绿着色，与航行灯一致。

测试：改动文件语法检查通过；本地静态服务器返回 200。

Interaction阶段 3 · 反馈打磨

换舷约定校准：标签与视觉统一

学生反馈：TWA +165° 时 UI 显示 Port，但帆仍在右舷，标签与视觉不一致。

  • 改为标准航海约定：TWA>0 = Starboard tack（帆在左舷），TWA<0 = Port tack（帆在右舷）。
  • 修正 src/main.js 的 sailSide 符号映射与 Sailboat.js 的帆镜像渲染。
  • 更新相关注释，确保 HUD 标签、帆的视觉侧、真实航海术语三者一致。

测试：改动文件语法检查通过。

Interaction阶段 3 · 反馈打磨

HUD 帆侧：从航海术语到直观位置

学生反馈：TWA -26° 时 HUD 显示 Port，但帆仍在船的右侧；希望标签直接对应帆在模型上的位置。

  • HUD 将“舷 Tack”改为“帆侧 / Sail Side”，并按帆的实际位置显示：帆在左舷标“左舷 Port”，帆在右舷标“右舷 Stbd”。
  • 保留物理约定：TWA>0 时帆在左舷，TWA<0 时帆在右舷；仅调整文字映射使其与玩家直观一致。
  • 换舷提示 toast 同步取反，颜色保持左红右绿，与航行灯一致。

测试：改动文件语法检查通过；本地服务器返回 200。

Interaction阶段 3 · 反馈打磨

帆镜像修正：真正翻到背风侧

学生反馈：TWA +160° 时帆仍在船右侧（风来的同侧），模型没有反转。

  • 复现：用浏览器截图确认风向 090°/航向 000° 时，帆出现在右舷（风来向同侧），而非左舷（背风侧）。
  • 修正：重新统一 sailSide 语义——sailSide>0 表示帆在左舷（port），sailSide<0 表示帆在右舷（starboard）；TWA>0 时 sailSide=+1，TWA<0 时 sailSide=-1。
  • 修正 Sailboat.js 镜像方向为 sailSide>0 ? π : 0，并把 HUD 的 isPort 判定改回 sailSide > 0。

测试：node --check 全部通过；浏览器截图验证帆现在位于背风侧（与风来向相反）。

Interaction阶段 3 · 反馈打磨

换舷可见性再强化：橙色标记 + 冷却机制

学生反馈：仍旧没有看到模型有反转，希望帆的左右翻侧更明确。

  • 在帆后下角（clew）增加高对比度橙色发光标记球，帆翻侧时标记球从船的一侧明显移到另一侧。
  • 帆材质增加轻微自发光、横桁加粗，让帆在暗光海面更醒目。
  • 自动换舷由“15°死区”改为“0.45s 冷却”：船一旦穿过风帆立即翻到背风侧，避免在风眼前小角度徘徊时帆卡在错误侧。

测试：node --check 通过；浏览器截图验证风 090° 时帆/标记在左舷，风 270° 时帆/标记在右舷。

Interaction阶段 3 · 关卡节奏

Level 2 顶风死锁修复：从“无法前进”到“抢风教学”

学生反馈：Level 2 开局是顶风航向，但船无法前进，调整方向也很慢。

  • 根因：船初始航向正朝目标（TWA=0°）落在禁航区，推力几乎为零；速度≈0 时 BoatDynamics 的舵效 ∝ speed，导致完全无法转向。
  • 转向速率加 25% 最低舵效下限，即使无速也能缓慢把船转出顶风区，打破死锁。
  • 关卡加载时若“朝目标方向”落在禁航区内，初始航向自动偏到抢风角（45°）一侧；Level 2 开局即可获得约 1.5 kn 航速。
  • HUD 新增红色禁航区警示，罗盘红弧范围与物理 no-go zone 对齐，提示玩家“转向离开，走之字形靠近目标”。

测试：node --check 全部通过；浏览器截图验证开局能前进、驶入顶风区后警示出现、转向离开后航速恢复。

Reflection覆盖 Interaction 04–17

可读性、反馈与关卡节奏到位

  • 游戏变化：界面不再遮挡场景，目标与罗盘信息清晰可辨，中英观众均可访问；换舷成为可见、可感知的核心动作。
  • AI 帮助：连续多轮根据截图反馈快速迭代 HUD 布局与可读性，并定位“帆永不翻侧”的根因、落地自动换舷。
  • 与核心转变的关系：界面清理后玩家注意力回到“读风与航线”，而非被 UI 干扰；自动换舷让 Level 2（顶风限时）的教学成立。
⏳ 待学生反思：当前界面是否足够清晰？自动换舷手感是否自然？是否要加入“航迹 vs 计划航线”对比反馈？
